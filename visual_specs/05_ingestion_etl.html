A.X.I.O.M — 05 Ingestion ETL & Stale Index Purge

Async Write Pipeline · Soft-Delete Versioning · Department Retention Policies · CQRS Architecture
30-Second Pitch: A.X.I.O.M. separates its data lifecycle into two independent sides: the Read Side (live user query serving) and the Write Side (background document ingestion and index management). This CQRS (Command Query Responsibility Segregation) architecture ensures that uploading a 4-hour training video or ingesting 500-page contract never blocks or delays live user queries. The ETL pipeline runs in an async Celery task queue, processing Extract → Transform → Load in the background. The Stale Index Purge system uses a Soft-Delete strategy (is_active_version = false) combined with Department-Level Retention Policies to guarantee that different business units (HR vs Legal vs Engineering) enforce their own document lifecycle rules without a central policy bottleneck.

ETL Pipeline Execution Steps

Step-by-step async execution after file upload:

  1. Admin uploads file → API returns HTTP 202 Accepted + Task_ID immediately (user never waits)
  2. Celery Worker picks up Task_ID from Redis Queue
  3. EXTRACT: Parse modality (PyAV for video, WhisperX for audio, ColPali renderer for PDF/images, text parser for docs)
  4. TRANSFORM: Chunk (VAD/Scene-Cut/Token Window) → Generate embeddings → Validate data integrity contracts
  5. PURGE STALE: Apply Department Retention Policy → Soft-delete or coexist old version
  6. LOAD: Write new active vector records to Qdrant with full metadata payload
  7. INVALIDATE CACHE: Delete matching Redis cache keys pattern: DEL CACHE:*:DOC_ID:*
  8. STATUS UPDATE: Mark Task_ID as COMPLETE in Redis

Soft-Delete Versioning System

The 3-State Version Lifecycle

v1.pdf (ACTIVE)
  │
  │ New version v2.pdf uploaded
  ▼
v1.pdf: is_active_version = false, soft_deleted_at = '2026-07-30'
v2.pdf: is_active_version = true  ← All live queries retrieve this
  │
  │ 30-day retention window
  ▼
[DAY 31] CRON Job hard-purges v1.pdf vectors permanently

Qdrant Version Payload Schema

{
  "doc_id": "HEALTH_POLICY",
  "file_version": 2,
  "is_active_version": true,
  "soft_deleted_at": null,
  "ingested_at": "2026-07-30T10:00:00Z",
  "superseded_by": null
}

Why Soft-Delete over Hard-Delete

  • Instant Rollback If v2 has errors, flip v1 back to active in 1 Qdrant payload update
  • Audit Trail Compliance teams can query historical versions for any point in time
  • Zero DB Lock Soft-delete is a single payload field update — no table locks, no index rebuilds

    }
  }
}

Why Different Departments Need Different Strategies

  • HR/Operations: Old policies must be retired immediately to prevent employees filing claims under outdated rules
  • Legal: Old vendor contracts remain legally binding in court — both versions must be queryable
  • Engineering: Old API docs must remain active while legacy clients still use API v1.0

Three Real-World Ingestion Examples

Example 1: Policy PDF Update HR — Soft Delete

  • HR uploads Health_Benefits_2026_v2.pdf
  • ETL detects department: HR → strategy: SOFT_DELETE_PREVIOUS
  • v1 vectors: SET is_active_version = false, soft_deleted_at = TODAY
  • v2 vectors ingested: is_active_version = true
  • Redis cache DEL CACHE:*:HEALTH_BENEFITS:*
  • Day 31: CRON hard-purges v1 vectors

Example 2: Video Training Re-Upload Engineering — Multi-Version

  • Engineering uploads Deploy_Microservices_v2.mp4
  • ETL detects department: ENGINEERING → strategy: MULTI_VERSION_COEXISTENCE
  • v1 video vectors remain: is_active_version = true
  • v2 video vectors ingested: is_active_version = true
  • Employees can now ask: 'What changed between v1 and v2 of the deployment guide?'

Example 3: GDPR Right to be Forgotten Hard Delete

  • Compliance event: client_id CLIENT_709 requests full erasure
  • Qdrant: DELETE WHERE payload.client_id == 'CLIENT_709'
  • Redis: DEL CACHE:*:CLIENT_709:*
  • S3: Delete all raw audio/PDF files for CLIENT_709
  • Compliance log: Record deletion event with timestamp for audit
